# Cvar bridge and tabbed options dialog for VGUI1 (v2)

This change adds a function-pointer bridge layer allowing VGUI1 controls to read/write engine cvars without linking the engine directly, then builds a tabbed Options dialog on top of it. Three reusable control classes (CvarCheckButton, CvarSlider, CvarTextEntry) consume the bridge; VguiOptionsDialog assembles them into an 8-tab Frame exposed via exported `VGUI_ShowOptions()`/`VGUI_HideOptions()`. The v1 review's five issues have been addressed: CvarSlider gained a float-scaling constructor, the dangling `g_pOptionsDialog` is nulled on shutdown, `hud_scale` now has 11 discrete steps mapped to 0.0–2.0, and `VGUI_GetRootPanel` is properly declared in `VGUI_CvarBridge.h`.

**Watch for:** Cancel button cannot undo slider changes because `fireIntChangeSignal` writes the cvar live on every drag (confirmed). `OptionsOKSignal`/`OptionsCancelSignal` hold a raw pointer to the dialog with no invalidation mechanism — safe today but fragile if dialog lifetime changes (likely).

**Verdict**: APPROVED

## High-level view

CvarSlider's float-scaling path uses a second constructor storing `_cvarMin`/`_cvarMax` with linear interpolation in `sliderToFloat()`/`floatToSlider()`. All audio, video, and HUD sliders now use this path; the integer-only constructor remains for `topcolor`/`bottomcolor`/`sensitivity`.

The Cancel/OK semantic has a gap: both CvarSlider and CvarCheckButton write the cvar live (on slider release and on click respectively), so by the time the user clicks Cancel, all controls have already mutated engine state. Cancel is effectively "close" — it neither reverts nor differs from OK in outcome. The standard GoldSrc Options dialog exhibits the same live-write behavior, so this may be intentional.

<summary>Issues (2)</summary>

1. **Cancel doesn't revert slider/checkbox changes** — `fireIntChangeSignal` and `internalMousePressed` write the cvar immediately. Cancel hides the dialog without restoring prior values. If true cancel semantics are desired, either defer cvar writes until OK or snapshot values on open and restore them on cancel.
2. **ActionSignal pointers to dialog** — `OptionsOKSignal` and `OptionsCancelSignal` store a raw `VguiOptionsDialog*` with no matching `delete`. If the dialog is ever destroyed and recreated, the signal objects hold dangling pointers. Low risk given current single-instance lifetime.

## Cancel semantics vs. live cvar writes

CvarSlider overrides `fireIntChangeSignal()` to write the cvar immediately:

```cpp
void CvarSlider::fireIntChangeSignal()
{
    Slider::fireIntChangeSignal();
    if (_scaled)
        VGUI_SetCvarFloat(_cvarName, sliderToFloat());
    else
        VGUI_SetCvarFloat(_cvarName, (float)getValue());
}
```

`Slider::internalMouseReleased` calls `fireIntChangeSignal()` on every drag completion. CvarCheckButton does the same in `internalMousePressed`. The Cancel button calls only `setVisible(false)` — no rollback, no `resetAll()`. The OK button's `applyAll()` is redundant since all values were already written live.

If this is live-preview behavior by design, the OK/Cancel distinction is cosmetic only. If deferred-commit semantics are intended, remove the live writes from `fireIntChangeSignal` and `internalMousePressed` and only write on `apply()`.
