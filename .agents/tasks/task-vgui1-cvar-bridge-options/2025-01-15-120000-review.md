# Cvar bridge and tabbed options dialog for VGUI1

This change adds a function-pointer bridge layer so that VGUI1 controls can read and write engine cvars without linking directly to the engine, then builds a full Options dialog on top of it. The bridge is initialized by the engine calling `VGUI_SetCvarFuncs()` at runtime; three reusable control classes (CvarCheckButton, CvarSlider, CvarTextEntry) consume the bridge; and VguiOptionsDialog assembles them into an 8-tab Frame exposed via `VGUI_ShowOptions()`/`VGUI_HideOptions()`.

**Watch for:** CvarSlider uses integer-only ranges, which silently truncates cvars whose natural domain is fractional (volume 0.0-1.0, gamma 1.8-3.0) (confirmed). The dialog is never destroyed on `VGUI_Shutdown`, leaving a dangling pointer to a freed panel tree (confirmed). All cvar controls call `reset()` during construction, which invokes bridge functions that are null until the engine calls `VGUI_SetCvarFuncs` -- safe today (returns 0/empty string) but brittle if the bridge contract changes (likely).

## High-level view

The bridge is five static function pointers behind thin wrappers in `vgui` namespace, initialized atomically via one exported C function. Controls consume the bridge only through `VGUI_CvarBridge.h`. The wrappers return safe defaults (0.0f, empty string) when pointers are null, which is what makes the early `reset()` calls during construction benign -- but there's no explicit contract guaranteeing those defaults survive future changes.

CvarSlider's integer-only mapping is the largest behavioral gap. Cvars like `volume` (engine range 0.0-1.0) and `gamma` (engine range ~1.8-3.0) are given slider ranges 0-100, but the slider writes the raw integer value back with `VGUI_SetCvarFloat(_cvarName, (float)getValue())`. There is no scale/offset transform, so "volume 50" writes the literal float 50.0 to the cvar, not 0.5. Either the slider needs a float mapping layer, or the cvar names here don't map to the standard GoldSrc cvars with those names.

The dialog's lifecycle has a hole: `VGUI_Shutdown` deletes `s_rootPanel` and all its children (including the dialog since `setParent(root)` was called), but `g_pOptionsDialog` is never nulled. The next `VGUI_ShowOptions` after a vid_restart dereferences freed memory.

<details>
<summary>Issues (5)</summary>

1. **CvarSlider integer truncation for fractional cvars** -- Sliders for `volume`, `suitvolume`, `gamma`, `brightness` write raw integers (0-100) instead of the float range the engine expects. Add a min/max float mapping or use a float-based slider.
2. **Dangling g_pOptionsDialog after shutdown** -- `VGUI_Shutdown` destroys the root panel tree (including the dialog), but `g_pOptionsDialog` is never reset to null. Next `VGUI_ShowOptions` dereferences freed memory. Null the pointer in shutdown or register a destructor callback.
3. **hud_scale slider range 0-2 too coarse** -- With only 3 discrete positions (0, 1, 2), the slider is barely interactive. If `hud_scale` is truly integer-valued this is fine, but if fractional values matter, the range needs expansion.
4. **CvarCheckButton bypasses CheckButton toggle logic** -- `internalMousePressed` manually flips selected state and writes the cvar, then falls through to `Panel::internalMousePressed` (skipping CheckButton's own handler). If CheckButton::internalMousePressed also toggles, the state double-flips. Verify the base class behavior.
5. **No VGUI_GetRootPanel declaration in a header** -- The function is forward-declared locally in VguiOptionsDialog.cpp. Any future consumer of the root panel will duplicate this declaration. Add it to VGUI_CvarBridge.h or a dedicated header.

## CvarSlider integer mapping vs. engine cvar domains

CvarSlider operates on integer values exclusively. The constructor calls `setRange(minVal, maxVal)` with int parameters, `reset()` casts the cvar float to int, and `apply()` casts `getValue()` back to float. This works for cvars like `topcolor` (0-255) or `sensitivity` (1-20 with integer steps).

It breaks for the Audio and Video tabs. The engine `volume` cvar expects 0.0-1.0. The slider is given range 0-100, so dragging to the middle writes 50.0 -- fifty times the maximum meaningful value. Same issue with `gamma` (engine expects roughly 1.8-3.0), where the slider writes 0-100 raw. The acceptance criteria mention "range 0-100, representing 0.0-1.0 scaled" but no scaling code exists in `CvarSlider::apply()` or `fireIntChangeSignal()`.

A minimal fix: add `_scale` and `_offset` floats to CvarSlider so `apply()` writes `offset + (getValue() - minVal) * scale / (maxVal - minVal)` instead of the raw integer. Alternatively, create a `CvarFloatSlider` subclass.

## Dialog lifecycle and the dangling pointer

```
VGUI_Shutdown():
  s_rootPanel->setSurfaceBaseTraverse(0);
  delete s_rootPanel;  // destroys all children, including g_pOptionsDialog
  s_rootPanel = 0;

// But g_pOptionsDialog still points to freed memory.
```

If the engine calls `VGUI_Startup` again (resolution change, vid_restart), then `VGUI_ShowOptions` checks `if (!g_pOptionsDialog)` -- the pointer is non-null, so it calls `resetAll()` on a dead object. This is a confirmed use-after-free path.

Fix: either null `g_pOptionsDialog` from `VGUI_Shutdown` (requires an accessor or a registered callback), or don't parent the dialog to `s_rootPanel` and manage its lifetime independently.

## CvarCheckButton double-toggle risk

```cpp
void CvarCheckButton::internalMousePressed(MouseCode code)
{
    setSelected(!isSelected());
    VGUI_SetCvarFloat(...)
    fireActionSignal();
    Panel::internalMousePressed(code);  // skips CheckButton::internalMousePressed
}
```

By calling `Panel::internalMousePressed` instead of `CheckButton::internalMousePressed`, this avoids a potential double-toggle from the base class. But it couples to an undocumented assumption about CheckButton's internal toggle behavior. If CheckButton::internalMousePressed doesn't actually toggle (only fires signals), then the override is doing redundant work. If it does toggle, and a future refactor calls the base class properly, the state flips twice. Worth verifying against the VGUI1 CheckButton implementation.

## Test coverage

No automated tests accompany this change. The acceptance criteria rely on compile-only verification. Not tested:

- Controls read correct initial values from cvars
- `applyAll()` writes back expected values
- Dialog survives a startup/shutdown/startup cycle (the dangling pointer issue)
- Sliders clamp out-of-range cvar values correctly

The slider value-mapping issue would have been caught by even a simple unit test of CvarSlider with a mock bridge.
